# 广拓生物网站后台：产品与落地方案

> 版本：2026-09-02。本文描述客户交付版网站后台的产品边界、信息架构、内容模型和技术落地方式。仓库中的 `/admin/` 已接入本地 SQLite 内容服务，可登录、保存草稿、上传图片和发布；正式上线仍需把该服务部署到带 TLS、持久磁盘和备份的私有运行环境。

当前可实测范围包括首页首屏、6 个固定页面、21 款产品、41 种膜型、4 份专利资质、中文文章、图片素材与发布记录。以上内容均支持保存草稿、版本冲突保护和单条发布；公开网站只读取已经发布的版本。

## 1. 交付目标

客户运营人员不需要理解代码、页面结构或部署流程，也能安全完成三件事：

1. 新建和发布文章。
2. 修改网站页面、公司资料和产品信息。
3. 替换展示图片，确认影响范围后发布。

成功标准：第一次使用、没有技术培训的人员，能在 5 分钟内找到首页主标题并完成修改、预览、发布前检查和发布；发布完成前，公开网站始终保留上一个已发布版本。

明确不交给普通运营人员的能力：自由搭建页面、修改字体和品牌色、输入 HTML/CSS/JSON、调整路由、编辑 3D 模型与生成参数、管理插件、查看 API 或部署配置。

## 2. 调研后的设计结论

主流内容后台采用的共同方法不是开放更多技术能力，而是锁定结构，只开放内容：

| 产品 | 借鉴点 | 对本项目的应用 |
| --- | --- | --- |
| Webflow Content Editor | 在真实页面上点击文字和图片编辑；内容角色不能改结构、样式或代码；CMS 条目自动保存为草稿后再预览、发布 | 首页、公司资料采用“页面位置图”；固定版式不可破坏 |
| Shopify Admin | 统一文件库可在文章和页面中复用；可按使用情况筛选；媒体有焦点和替代文字 | 图片库记录使用位置；默认“只替换当前位置” |
| WordPress Gutenberg | 区块化写作、草稿、预览和修订历史 | 文章只开放段落、标题、图片、列表、引用和规格表等受控区块 |
| Sanity Studio | Visual Editing 将真实预览与字段关联；点击页面元素可定位字段 | 正式后台优先采用可配置的视觉编辑和独立预览环境 |
| Contentful | 编辑器与 Live Preview 并排；Inspector 可从预览定位字段 | 文章编辑器固定右侧预览；嵌入失败时提供新窗口预览 |
| Strapi | Collection 管多条内容，Single Type 管唯一资料；Draft/Published 状态清楚 | 底层按“文章集合 / 公司资料单例”建模，但界面不出现技术术语 |

这些产品也暴露出几个需要规避的问题：同一内容在多个标签页修改可能互相覆盖、全局图片修改影响所有引用、插件或动态区过多导致认知负担。广拓后台必须显示自动保存时间、具体影响页面、发布结果和恢复入口。

## 3. 产品方向

后台名称使用“广拓网站内容工作台”，不使用 CMS、Content Manager 等技术词。

视觉方向是“临床工作台”：米白工作面、深墨色导航、品牌粉色作为唯一强调色；状态色只用于已发布、待处理和高风险字段。后台不是数据大屏，首页只展示下一步动作。

核心识别点是“页面位置图”：用户看到首页缩略图和 1–5 个可编辑位置，点击位置后填写对应业务字段，不需要理解 Hero、Section、Component 或字段 key。

## 4. 信息架构

客户侧主导航保留：

- 工作台
- 网站首页
- 网站页面
- 产品
- 膜型
- 专利资质
- 文章
- 图片与文件
- 发布记录

工作台首屏提供三个主要动作：

- 写新文章
- 维护产品
- 上传图片

下面只显示“待我处理”“语言版本”“最近修改”。访问量、服务器状态、数据库、部署日志等不进入客户日常后台。

## 5. 核心流程

### 5.1 文章

```text
写新文章
  → 标题 / 摘要 / 分类 / 封面 / 正文 / 关联产品
  → 电脑与手机预览
  → 保存草稿
  → 检查必填内容和发布范围
  → 确认立即或定时发布
```

编辑器只开放：正文段落、二三级标题、图片和说明、列表、引用提示、规格对比表、最多 3 款关联产品。Word 或网页内容粘贴时清理字体、颜色和多余样式。

### 5.2 页面信息

```text
选择页面
  → 点击页面位置
  → 修改固定业务字段
  → 查看修改后效果
  → 保存草稿
  → 检查影响页面和语言
  → 确认发布
```

首页字段使用普通运营语言：主标题上方短句、主标题、简介、主按钮文字、主按钮打开页面、首屏图片、推荐产品、水凝胶专长介绍、制造与品控图片、合作市场、底部行动提示。

### 5.3 图片替换

```text
选择页面和位置
  → 查看当前图片和使用位置
  → 上传或选择新图
  → 按目标比例裁切并选择视觉重点
  → 对比替换前后
  → 只替换当前位置（默认）
  → 预览并确认发布
```

正在使用的图片不能直接删除。错误应写明：“这张图片正在首页和制造与品控页使用，共 2 处。请先替换这些位置。”

### 5.4 发布状态

```text
草稿 → 发布前检查 → 已排期 / 发布中 → 已发布 → 已撤下
```

编辑已发布内容时，创建新草稿；线上版本保持不变。恢复历史版本只生成新草稿，不能直接覆盖线上内容。发布服务失败不是内容状态，失败后线上内容不变。

## 6. 多语言规则

中文作为默认原稿，英文、法文、西文、俄文和阿文分别维护。

- 修改中文后，已有翻译标记为“需要更新”，不覆盖旧译文。
- 旧语言版本继续在线，直到新翻译检查并发布。
- 新文章可以只发布选定语言；未发布语言不显示中文兜底。
- SKU、规格、MOQ、专利号和共用图片只维护一次，供所有语言使用。
- 自动翻译只能生成草稿，不能直接发布。
- 翻译界面左侧固定中文，右侧填写目标语言。
- 阿文必须提供从右向左的真实页面预览。

## 7. 单人维护模式与发布安全

客户侧只配置一个“网站维护人”账号。该账号可以新建和修改草稿、上传图片、预览、发布、排期、撤下以及恢复历史版本。后台不设置内容人员之间的流转、退回或批准步骤；账号与技术配置由交付方在后台平台中维护，不进入客户的日常导航。

单人使用不等于取消安全保护：生产后台仍需登录保护、多因素验证或可靠的账号恢复方式、自动保存、操作记录、发布历史和版本恢复。MOQ、功效、认证、专利权人和公司联系方式属于高风险字段，发布前必须补充依据或修改说明，并在确认页展示修改前后内容；缺少依据时不能发布。

## 8. 与当前网站匹配的内容模型

| 内容类型 | 关键字段 | 当前迁移来源 |
| --- | --- | --- |
| 网站设置（单例） | 展示名称、法定名称、Logo、公司事实、地址、公开电话与邮箱、默认搜索展示、页脚 | `src/components/header.tsx`、`footer.tsx` 与多个数据文件中的重复事实 |
| 固定页面 | `home/products/customization/process/factory/patents/about/contact`，每页固定区块、多语言文案、图片槽位、搜索展示 | `src/data/site-copy.ts`、`company-page-copy.ts`、`site-visuals.ts` |
| 产品分类 | 稳定 ID、名称、介绍、主图、排序、发布状态 | `src/data/catalog.ts` 三个固定分类 |
| 产品 | 不可变 SKU、稳定链接、分类、多语言名称/介绍/特点/护理方向、规格、MOQ、包装、主图、图库、状态 | `src/data/catalog.ts` 的 21 款产品 |
| 技术膜型 | 固定 ID、分类、材料体系、多语言名称、规格、MOQ、图片、证据 | `src/data/hydrogel-formats.ts` 的 41 种膜型 |
| 专利与资质 | 类型、编号、权利人、机构、有效期、证书原图、业务关系、公开说明、核验状态 | 专利页与产品详情页的两套数据合并 |
| 文章 | 稳定 ID/链接、状态、发布时间、多语言标题/摘要/正文、封面、作者、栏目、关联产品、搜索展示 | 当前不存在，需要新建 |
| 图片与文件 | 原图、宽高、大小、格式、焦点、六语言图片说明、用途、来源与使用权、发布状态、使用位置 | `public/assets/**` 的 121 个本地资产 |

SKU、产品链接和分类 ID 发布后锁定。公开产品使用“归档/撤下”，不提供永久删除。3D 模型路径、模型位置、Logo 锚点等字段保持开发者专用。

迁移时首先修正一个现有风险：当前产品记录全部带 `draft` 状态，但产品页和 sitemap 仍读取完整产品数组。内容接入层必须统一使用 `published` 查询。

## 9. 推荐技术架构

### 9.1 为什么 `/admin/` 需要独立内容服务

当前 `next.config.ts` 使用 `output: 'export'`，生产部署是 S3 + CloudFront 静态站。项目内 Next.js 16.3.1 文档明确，静态导出不支持登录 Cookie、Draft Mode、Server Actions、ISR、依赖请求的写入路由或未在构建时枚举的动态页面。

因此，`/admin/` 只承担公开的浏览器界面壳，登录、草稿、SQLite、原始上传和发布操作全部由独立内容服务处理。仅添加 noindex 不能保护后台；公开静态包中不得包含密码、会话、数据库或草稿。

### 9.2 当前落地：独立内容服务 + 静态前台快照

```text
客户运营人员 → `/admin/` 静态界面
              → 独立 CMS 服务（登录、SQLite、私有草稿图片）
              → 严格校验后的 `content/published-content.json`
              → 同源 `public/uploads/cms/` 已发布图片
              → Next 静态构建 → S3 + CloudFront
```

本地联调用 Node 内容服务、SQLite 和私有媒体目录；发布动作只导出允许公开的首页、页面、产品、膜型、专利资质和文章字段。上线时保持接口和快照契约不变，可把数据库换成 PostgreSQL、原图换成私有 S3，并由发布动作触发 CodeBuild/GitHub Actions。构建失败时不切换线上版本。

### 9.3 预览

现有静态站不能使用 Next Draft Mode。正式方案应另建仅登录用户可访问的预览应用，或使用 Sanity Presentation Tool 对接独立预览环境。右侧嵌入预览失败时必须提供“在新窗口查看预览”。

### 9.4 内容接入层

前台页面不直接依赖 CMS SDK。新增统一内容层：

```text
src/lib/content/schema.ts
src/lib/content/server.ts
src/lib/content/queries.ts
src/lib/content/dto.ts
```

建议接口：

```ts
getSiteSettings(locale)
getPage(key, locale)
listPublishedProducts(locale)
getPublishedProductBySlug(slug, locale)
listTechnicalFormats(category, locale)
listPublishedArticles(locale)
getPublishedArticleBySlug(slug, locale)
```

Next 在构建阶段读取已发布内容。文章详情路由使用稳定的跨语言 slug 和 `generateStaticParams()` 生成静态页面。图片若使用 CMS CDN，需要同步修改 Next 图片白名单与 CloudFront CSP；更稳妥的当前架构是发布时将已确认媒体同步到同源 S3。

## 10. 实施顺序

1. **已完成基础闭环**：单账号登录、SQLite 草稿、图片上传、发布记录、操作日志和公开内容快照。
2. **已完成文章闭环**：文章列表、编辑、封面、发布以及前台文章列表和详情。
3. **已完成固定内容迁移**：首页首屏、6 个页面、21 款产品、41 种膜型和 4 份专利资质均可在后台维护。
4. **下一阶段增强**：多语言逐语种维护、历史版本恢复、定时发布、图片使用位置和更完整的发布前检查。
5. **交付培训**：用“写文章、改页面、维护产品、换图片、发布内容”五个场景验收。

## 11. 上线验收

- 编辑已发布内容但未发布时，公开站仍显示旧版本。
- 网络中断后可恢复自动保存草稿。
- 修改中文后，其他语言标记“需要更新”且旧译文不被覆盖。
- 阿文预览使用 RTL，数字和图片不错误镜像。
- 替换多处使用的图片时，默认只影响当前位置。
- 正在使用的图片不可直接删除，并准确列出使用页面。
- 网站维护人可直接发布、排期或撤下内容，无需人员流转。
- 专利权人、MOQ 等高风险字段缺少依据或修改说明时不能发布。
- 恢复历史版本只生成新草稿。
- 发布失败明确提示“线上内容没有改变”。
- 发布确认页列出将更新的页面、语言和影响位置。
- 所有成功、失败、空状态和不可用状态都有明确下一步。
